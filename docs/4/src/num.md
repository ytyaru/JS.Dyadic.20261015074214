# num.js

IEEE754のクソ仕様を排除した数型を作る。

```javascript
num(v)          // Number.isFinite(v)
num.dya(v)      // 二進分数（二進有理数）
num.fin(v)      // Number.isFinite(v) && SAFE範囲内
num.int(v)      // Number.isSafeInteger(v)
```

型|NaN|Infinity|SAFE外|SAFE内|浮動少数
--|---|--------|------|------|--------
num|❌|❌|⭕|⭕|⭕
num.dya|❌|❌|❌|△|⭕
num.fin|❌|❌|❌|⭕|△
num.int|❌|❌|❌|⭕|❌

Number型は数として扱えるものであるべきだ。ところが実装であるIEEE754規格は通常の数ではないものが大量にある。そのせいでバグの温床が無数にある状態だ。これを改善したくてnum.jsを作る。

Number型はIEEE754規格に基づく。これによるとNaN,Infinity,-Infinity,MAX_VALUEという特殊な数値がある。これらは算術計算を破綻させる数だ。よって使えなくする型を用意すべき。NaNは非数であり数型に属する値として矛盾している。用途としては計算を続行させ他の計算結果を得るためだ。途中で例外発生したらそれが実現できない。だがそのせいで破綻した計算があることと、その問題箇所がどこであるかが分かりにくくなってしまいバグの温床となる。Infinityも同様に通常の有限算術では用いないしNaNと同様に登場したら以降はすべてInfinity汚染しまともな計算ができない。MAX_VALUEはInfinityの手前の値だが、そもそもSAFE値を超過した時点で整数最小値1を超過しており人間がまともに扱える数ではない。よってこれらは通常、排除すべき値である。

Number型はIEEE754規格に基づく。これによるとSAFE値（Number.MIN_SAFE_INTEGER〜Number.MAX_SAFE_INTEGER）（-2**53-1〜+2**53-1）の範囲を超過すると、整数の最小単位が1を超過した数になってしまう。それを人間が理解し計画的に運用することはできない。故にSAFE範囲内だけを数として扱うべきである。Number型にはそれができない。

JSで扱える数はNumberとBigIntだ。このうちNumberの制限版を作るべきである。その型をNumと仮名する。上記によるとNumで扱うべき数はSAFE内の値のみだ。すなわち`(-2**53)-1〜(+2**53)-1`である。この数ならば整数の最小単位が1なので通常の数として扱える。算術計算を破綻させる特殊値もない。ただ、浮動少数を含めてしまうと、少数部分で誤差が発生する。その理由はNumber型が二進有理数だからだ。つまり小数部分がマイナス2のN乗単位（0.5, 0.25, 0.125, ...）でしか扱えない。ところが人間が実際に扱う数の単位は10進数だ。例えば十進数では自然な0.1などの値でも、浮動少数では誤差なく扱うことができない。この誤差は計算を重ねるごとに大きくなってしまう。これを解決するには10進少数decimal.jsを使うしか無いが、その実態は文字列でありNumber型でない。よって今回は対象外だ。

今回対象にするのはnum,fin,dya,intである。numとfinは同じだから実質3つだ。

finはいわゆるfloat型。JSではFinite有限数という型だ。どちらの名前にするか悩ましい。最も問題なのは少数で誤差が発生することだ。だがそれを理由に扱わないのはもっと不味い。C/C++言語時代からある一般的な型だからだ。

dyaはdiadic二進分数（二進有理数）型である。0.5,0.25,0.125,...のようにマイナス2のN乗単位で少数を扱う。この単位に従えば誤差が発生せず少数を扱える。もし誤差のあるfin値が代入されたら指定した丸め方法によってマイナス2のN乗単位の数に丸める。

intは整数型。いかなる浮動少数も扱えない。

# 

* 型
    * 型を定義する
    * 値が型に従っているか判定する
    * 値が型に従っていなければ例外発生する
* 値
    * 値を代入するときに所定の処理をする
        * Num型でない
            * ignore: 無視する（代入しない）
            * throw: 例外発生する（TypeError）
        * Num型だが範囲外
            * ignore: 無視する（代入しない）
            * throw: 例外発生する（TypeError）
            * floor/trunc/ceil/round/even: 丸める
            * overflow: オーバーフローする（上限・下限値でマスクしそれ以内の数にする）
            * stop: 停止する（上限・下限値で停止させる）
            * default: デフォルト値をセットする

本来ならば例外発生一択なのだ。それ以外ではバグの温床になりかねない。`* ignore: 無視する（代入しない）`という処理もありえるが、代入したコードを書いた上に正常終了してしまうからコードの字面上、代入されず無視されるようには見えない。だから代入されたと思ってしまう。これがバグ温床だ。問題箇所の特定が困難になってしまう。

プログラミングとは事前定義することだ。型定義とは事前にどうメモリを扱うか定義することだ。その約束を破った時点で例外発生させるべきである。さもなくば何も定義することができない。それをプログラムとは呼ばない。実行時にどんな破綻が起こるか不明でありそのパターンが無限に内包されたコードになる。JSは言語仕様上そうした未定義の塊だ。実行時エラーパターン爆発する言語仕様だ。それを少しでも抑制しようとするのが型定義でありnum.jsである。

ただ、超過時の処理を予め決めておけばそれはバグではなく仕様だと言える。たとえ超過時に代入を無視されようがオーバーフローしようが上限値停止しようが、そのようにすると明記すれば、仕様である。

ならば通常は例外発生することとし、引数次第では超過時の挙動を変更できるようにする構造が良いだろう。

```
class ???T { // 型
    constructor(isFn) {}
    is(v)  {} // 真偽値
    try(v) {} // 例外発生（trueの時は値を返す）
}
class ???V { // 値
    constructor(type, onSet) {}
    get v()  {}
    set v(x) {} // 代入処理
}
```
